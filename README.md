# pcldl

> PCL2 内置下载引擎（`Modules/Base/ModNet.vb`）的 1:1 复刻，Python 标准库实现，单文件，零依赖。

PCL（Plain Craft Launcher 2）是开源的 Minecraft 启动器，它那套下载引擎有个很不寻常的设计：**分片数量不预先决定，而是在下载过程中按"当前连接喂不喂得满带宽"动态生长**。这个仓库把它完整复刻了一遍，包括段级重试、多源容错、断点续传、令牌桶限速和合并校验。

```bash
python pcldl.py https://example.com/big.iso
```

## 特性

| 能力 | 说明 |
|---|---|
| 动态分片 | 先跑 1 段，喂不满才切；切"剩余最多"那段尾部的 40% |
| 边际收益判据 | 切完总速度涨不到 10% 就指数退避（1s→2s→4s→8s），不无脑堆线程 |
| 段级重试 | 每段一个独立 HTTP Range 请求，断了只回滚这一段，不影响别人 |
| 多源容错 | 多个 URL 视为镜像，失败计数到阈值自动换源，全灭才报错 |
| 断点续传 | 状态每 1s 落盘，Ctrl+C 或进程被杀后重跑同一条命令即可续传 |
| 自动降级 | 服务端无视 Range（返回 200）→ 判定不支持续传，改单流下载 |
| 令牌桶限速 | 容量取 `rate/10`（约 100ms 配额），不做 1 秒突发 |
| 完整性校验 | 大小 + SHA-256 / SHA-1 / MD5，校验失败自动删除产物 |
| 磁盘保护 | 开工前检查剩余空间 ≥ `size × 1.1`（分段方案峰值占约 2 倍） |
| 原版观感 | 进度条用 `1-(1-p)^0.9` 非线性映射 + 200ms 节流，尾部同样会"卡 99%" |

## 用法

```bash
# 最简
pcldl https://example.com/big.iso

# 指定输出 + 限速 8MB/s + 最多 8 个分片
pcldl https://example.com/big.iso -o D:/dl/big.iso --limit 8M -x 8

# 多镜像（同一文件的不同源，会自动负载 + 容错）
pcldl https://a.com/x.iso https://b.com/x.iso -o x.iso

# 下完校验
pcldl URL --sha256 3f7a...e21

# 需要 Cookie / Referer 的站点
pcldl URL --referer https://example.com/ --cookie "sid=abc; token=def"

# 自签证书 / 内网
pcldl URL -k

# 中断了？重跑同一条命令就是续传
pcldl URL -o D:/dl/big.iso
```

### 参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `-o, --out` | URL 文件名 | 输出路径；给目录则按 URL 取名 |
| `-n, --name` | — | 指定文件名 |
| `--limit` | `0`（不限） | 限速，支持 `4M` / `512K` |
| `-x, --connections` | `16` | 最大分片数（天花板，不是起始值） |
| `--min-piece` | `256K` | 小于这个剩余量就不再切 |
| `--chunk` | `64K` | 单次读取缓冲（PCL 用 16KB，Python 里 64KB 更划算） |
| `--sha256 / --sha1 / --md5` | — | 下载完成后校验 |
| `-H, --header` | — | 自定义请求头，可重复 |
| `--referer / --cookie / --ua` | — | 常用头快捷方式 |
| `-k, --insecure` | — | 跳过 TLS 证书校验 |
| `--linear` | — | 进度条线性显示（默认模拟 PCL 曲线） |
| `--no-resume` | — | 忽略已有断点，从头下 |
| `-q, --quiet` | — | 静默 |

## 原理

### 四个对象

```
NetManager  全局调度：120ms 心跳、采样速度、决定要不要切分片、令牌桶
   ├─ NetFile    一个文件：大小、段表、状态机、合并、校验
   │    ├─ Source   镜像源：URL + 失败计数 + 连接延迟
   │    └─ Segment  一段字节区间：一个独立请求 + 一个独立 .tmp
```

### 一次下载

1. **探测**：`Range: bytes=0-0`，从 `Content-Range: bytes 0-0/12345678` 拿总大小；返回 `200` 说明不支持续传。
2. **首段**：只起 **1 个** 段 `[0, size-1]`。不是一上来就开 16 个线程。
3. **动态生长**：调度器每 120ms 看一次总速度。若"切完上一刀后总速度涨幅 ≥ 10%"，说明还没吃满，就继续切；切的对象是**剩余量最大**的那一段，从它尾部切走 40%。
4. **落盘**：每段写自己的 `.tmp`，段内偏移 `pos - start`，不做随机写。
5. **合并**：全部下完后按 `start` 排序，逐段顺序读到 `<out>.part`，再 `os.replace` 原子改名。
6. **校验**：大小 → 哈希。失败删产物重来。

### 为什么不用"预先均分"

aria2 的 `-s N` 是先等分成 N 块。PCL 反着来，原因有三个：

- **小文件不该开线程**。200KB 的文件切 16 份，就是 16 次 TCP/TLS 握手，握手比传输还贵。
- **服务端差异巨大**。有的 CDN 单连接给 50KB/s，有的给 8MB/s，固定分片数在两种情况下都是错的。
- **切"最闲的那段"天然负载均衡**，不会出现"一段早下完了干等另一段"的长尾。

代价是每次切分都要重连，所以还有 `--min-piece` 兜底：剩余不足 512KB 就不再切了。

### 为什么每段一个 `.tmp`

代价很直接：**峰值磁盘占用约 2 倍**（所以有 1.1 倍空间检查，实际峰值会短暂超过 1.1，见"已知限制"）。

换来的是：
- 重试粒度 = 一段，回滚只需丢弃自己的 `.tmp`；
- 不需要维护共享文件句柄的写偏移和锁；
- 段被切断时（`end` 收缩），多读出来的几个字节留在 tmp 里，合并时按 `length` 读、多余字节丢弃，**零同步成本**。

### 那句"不支持断点续传"是怎么判断的

```python
# 我请求了 bytes=5000-，你却把整个文件的长度返回给我 → 你在无视 Range
if resp.status != 206:
    raise NoRangeSupport
```

百度网盘那类需要 Cookie/Referer 的链接，往往直接返回 403 的 HTML 错误页，`Content-Length` 和真实文件对不上，于是"下载失败"。

### 进度条为什么总在 99% 卡一下

显示值不是 `p`，而是 `1 - (1-p)^0.9`——前段压平、尾段拉开。加上 200ms 节流刷新，最后几个 MB 在视觉上被拉长，就变成"卡住然后突然跳完"。这是故意的。

## 和 aria2 / IDM 的差别

| | pcldl | aria2 | IDM |
|---|---|---|---|
| 分片策略 | 运行时按边际收益动态长 | 预先等分 `-s N` | 预先等分，固定 8/16 |
| 落盘方式 | 每段独立 tmp，合并串行 | 单文件随机写 + 位图 | 单文件随机写 |
| 断点续传 | 段级重试 + 状态文件 | 位图精确续传 | 位图精确续传 |
| 峰值磁盘 | ≈2× | 1× | 1× |
| 多源 | 一等公民 | 支持，需手工配 | 弱 |
| 依赖 | 无（标准库） | C++ 二进制 | 闭源 |

pcldl 的定位不是拼吞吐，而是在"源站三天两头挂、服务器爱乱回 Range"的环境里用最少的代码把成功率做到最高。

## 已知限制

- **峰值磁盘**：分段期间是 1×，合并时 `part` + 所有 tmp 同时存在，峰值接近 **2×**。1.1 倍检查只是提前拦明显不够的情况，不是精确峰值保证。
- **合并是串行的**：大文件最后一步受单盘顺序写限制，SSD 上不明显，机械盘上能感觉到。
- **状态每 1s 落盘**：强杀进程最多丢 1s 进度（测试里 32MB 文件多下了约 1.6MB）。
- **不支持 HTTP/2 多路复用**：一个分片一条 TCP 连接，和 PCL 一致。
- **镜像必须内容一致**：多源模式假设各 URL 是同一文件，不做事后一致性校验（只校验总大小和哈希）。
- **无代理自动发现**：走系统环境变量 `HTTP_PROXY` / `HTTPS_PROXY`。
